PROJET RÉSEAU & SÉCURITÉ

Architecture sécurisée Web avec pfSense & HAProxy

Conception d’une passerelle de publication sécurisée permettant d’héberger plusieurs applications HTTPS derrière une même adresse publique. pfSense filtre les connexions et HAProxy exploite le SNI pour acheminer chaque demande vers le serveur interne approprié.

🛡️ pfSense⚖️ HAProxy🔐 HTTPS / TLS🌐 SNI Routing📊 Health Checks L4
PRÉSENTATION

Contexte & besoin

L’entreprise doit rendre plusieurs applications Web internes accessibles depuis l’extérieur, tout en évitant d’exposer directement les serveurs et les informations sensibles de l’infrastructure.

Pourquoi HAProxy ?

Une redirection NAT classique du port HTTPS ne peut pointer que vers une seule destination. Plusieurs applications utilisant le même port public 443 nécessitent un reverse proxy capable de reconnaître le nom demandé et de sélectionner le serveur correspondant.

Objectifs

  • Centraliser les connexions HTTPS sur pfSense.
  • Router les demandes selon le nom SNI.
  • Conserver le chiffrement jusqu’aux serveurs internes.
  • Superviser la disponibilité des backends.
ARCHITECTURE

Architecture logique de la solution

Le routeur transmet le trafic publié vers pfSense. Le frontend HAProxy inspecte le SNI TLS, applique les ACL et sélectionne le backend applicatif adapté.

Flux logique : Internet → routeur → pfSense / HAProxy → serveur applicatif A ou serveur applicatif B.

🔐 Confidentialité : les noms de domaine, adresses IP, noms de serveurs, identifiants, mots de passe, certificats et clés privées sont volontairement masqués.
FONCTIONNEMENT

Parcours d’une connexion HTTPS

Le choix du serveur est effectué à partir du nom SNI présenté par le navigateur pendant la négociation TLS.

Résolution DNS

Le client résout le nom du service vers l’adresse publique de l’infrastructure.

Entrée Internet

Le routeur reçoit la connexion TCP destinée au service HTTPS.

Filtrage WAN

pfSense autorise uniquement les flux nécessaires vers le frontend HAProxy.

Inspection SNI

HAProxy lit le nom demandé dans le ClientHello TLS sans publier les détails internes.

Sélection du backend

Une ACL associe le nom demandé au serveur applicatif correspondant.

Transmission TLS

Le flux est transmis au backend HTTPS et la réponse revient au client.
