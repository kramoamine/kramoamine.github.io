Secure Web Architecture with pfSense & HAProxy

Designed a secure publishing gateway for hosting multiple HTTPS applications behind a single public address. pfSense filters inbound connections, while HAProxy uses SNI to route each request to the appropriate internal application server.

🛡️ pfSense⚖️ HAProxy🔐 HTTPS / TLS🌐 SNI Routing📊 L4 Health Checks
OVERVIEW

Context & requirement

The organization needs to make several internal web applications accessible externally without directly exposing servers or sensitive infrastructure details.

Why HAProxy?

A standard NAT rule for HTTPS can point to only one destination. When several applications share one public IP address and port 443, a reverse proxy is required to identify the requested host and select the correct server.

Project objectives

  • Centralize HTTPS connections on pfSense.
  • Route requests according to the TLS SNI name.
  • Preserve encryption to internal servers.
  • Monitor backend availability.
ARCHITECTURE

Logical solution architecture

The Internet router forwards published traffic to pfSense. The HAProxy frontend inspects TLS SNI, evaluates ACL rules and selects the corresponding application backend.

Logical flow: Internet → router → pfSense / HAProxy → application server A or application server B.

🔐 Confidentiality: real domain names, IP addresses, server names, credentials, passwords, certificates and private keys are intentionally hidden.
HOW IT WORKS

HTTPS connection flow

The destination server is selected from the SNI name presented by the browser during the TLS negotiation.

DNS resolution

The client resolves the service name to the infrastructure's public address.

Internet entry point

The edge router receives the TCP connection intended for HTTPS.

WAN filtering

pfSense allows only the required traffic to the HAProxy frontend.

SNI inspection

HAProxy reads the requested name from the TLS ClientHello without exposing internal details.

Backend selection

An ACL associates the requested service name with its application server.

TLS forwarding

The encrypted flow is forwarded to the HTTPS backend and the response returns to the client.
